# 银河漫游：面试讲述与产品判断

依据：当前本地实现 `ai-videogame/platform`，HEAD `34f5aa1`、用户提供的 BP，以及用户在 2026-11-03 补充的个人职责。本文是面试准备稿，不作为已发表的个人履历。当前代码包含参赛前后迭代，不将每个功能都归因为 72 小时内完成。

## 可以直接说的开场

> 我参加过北纬社区 AI 黑客松，和两位队友做了《银河漫游》，方向是把 AI 漫剧变成可以参与、可以改写的故事。三天 72 小时，我们完成原型并现场演示，获得冠军和最佳人气奖。
>
> 我负责产品定义、上下文与 Harness 的设计，也负责前端交互、视觉设计和影游 HUD。我们用《第零次》做具体体验，玩家进入一节异常车厢，看完一段影片，选择回应谁、调查什么，并在后续场景中保留时间与线索。创作端则把影片、角色、字幕和出口组织成节点，也接入了场景 Agent。
>
> 从产品角度，我会重点讲怎样让 AI 参与一次可控的改稿。提示词先约定协作方式，上下文围绕当前幕按需读取，Agent 通过受限工具编辑候选稿，Harness 负责过程记录、检查与提交。创作者可以查看过程、停止任务，或撤销整轮改动。下一步还需要让节点表达故事依赖，帮助作者看清一处修改会影响哪些后续情节。

## 优先从产品问题展开

网站的“产品判断与取舍”按以下五个话题叙述。可以结合自己参与的产品定义、上下文和 Harness 设计展开，具体实现仍按团队分工说明。

- 提示词约定什么。小光的身份是幕内创作搭档；明确先读状态、再改候选、最后检查和反馈的工作方式，完成标准落到实际作品。
- 上下文怎样控制。每幕独立会话，补入有限近期对话；当前状态重新从工具读取。按分区和引用读取资料。近期对话的摘录不等于模型线程全部历史已被严格裁剪，线程压缩仍由接入的 Codex 管理。
- Agent 能做什么。当前是一个场景 Agent，八个工具围绕读取、引用、编辑、校验与基础逻辑预览组织。没有已完成的多 Agent 自动生产流程。
- Harness 管什么。任务、工具边界、候选稿、执行记录、校验、版本冲突、取消与失败状态，以及整轮撤销。检查通过后自动写回草稿，目前没有每项修改都先由作者审批的流程。
- 下一步怎样约束故事。锁定设定、显示后续节点依赖、确认修改范围，是后续产品设想。当前结构校验不能证明故事语义连贯，也没有实现完整可视化差异合并。

核验入口为当前 HEAD `34f5aa1` 的 `shared/scene-tools.mjs`、`server/index.mjs:runAgent`、`shared/operations.mjs` 和 `PRODUCT-PRD.md` 的 P3 实现记录。代码只读核对，本轮没有重新调用真实模型。

## 工程追问备查

以下保留先前的实现核对，供追问时查证，不作为网站正文的主线。

### 1. 一套 HUD 如何同时供编辑器、Agent 与播放器使用

**问题。** 如果画布里存一份 HUD、表单里再存一份、播放器又写死一套，改了文字或时序，很容易只改到其中一处。

**实现。** 配置真相保存在 `scene.elements[].kit`。`makeHudKit` 创建 clock、subtitles、evidence、choices、chapter、focus 六类模板；画布卡片与元素使用相同 ID，卡片 metadata 从元素派生。表单、Agent 和 CLI 复用操作协议，播放器根据 Kit 类型呈现。无 Kit 的旧场景仍走 LegacyStage。

**可以这样讲。** “我关心的不只是做出一套 HUD，而是创作者能不能继续修改它。我们让显示时间、文案、观察点和选择锚点成为场景配置，编辑端与运行端消费同一份数据。这样设计既能落在具体影片里，也能移到下一幕。”

**容易追问。**

- 两种连线：`work.edges` 表达真正剧情流向；`scene.canvas.connections` 是幕内编辑关系。运行时按当前场景和 choice ID 查唯一 edge，不能仅靠画面上连了一条线就认定剧情已连通。
- 两种坐标：HUD 在 16:9 逻辑画面中用百分比；画布是独立平移、缩放坐标。移动编辑卡片不会等同于移动影片中的按钮。
- 更新语义：`hud.upsert` 只浅合并，传入 `kit` 会替换整个对象；改一个字段也要保留旧配置。数组按完整数组更新。
- 边界：当前是六类可配置 Kit，字幕等仍有固定皮肤布局；没有任意皮肤市场、多实例自由编排或视觉对象跟踪。

代码入口：`shared/hud-kits.mjs`、`shared/operations.mjs`、`src/playground/HudKitEditor.tsx`、`Stage.tsx`、`CinematicStage.tsx`、`docs/HUD-NODE-REUSE.md`。

### 2. 为什么跨幕时间、记录不能放在 HUD 组件里

**问题。** Stage 随场景重新挂载，如果每个时钟自己建计时器，容易重置、重复扣时；回看影片也可能重复收录线索。

**实现。** Player 是会话状态宿主。`hudClocks` 按 clockId 跨幕保存，使用视频时间的正向增量推进，同一幕同 ID 去重。暂停、记录面板、后台、片尾等待和预览不消耗时间；回退定位不增加剩余时间。`hudEvidence` 保存发现 ID，去重后从当前作品解析记录内容。存档保存时间、剧情状态、事件触发记录、HUD 状态与作品版本。

**可以这样讲。** “我把影片时间和故事时间分开理解。影片可以暂停、回看或切换，而玩家的旅程状态需要连续。组件只负责显示，跨幕状态由 Player 持有，切幕不会重新开始一趟旅程。”

**容易追问。**

- 定时事件按每次进入场景只触发一次，用 fired 集合避免一次播放中重复结算；重新进入的语义与全局唯一奖励要分别设计。
- 作品版本不匹配时拒绝恢复，避免旧存档里的节点或选择在新图中不存在。这里没有实现自动迁移任意旧存档。
- 随身记录是已发现内容的索引，不等于可消耗背包。钥匙使用、合成与全局奖励仍需显式玩法状态。

代码入口：`Player.tsx`、`shared/hud-kits.mjs` 的 `initialHudClocks / advanceHudClocks / collectHudEvidence / resolveHudEvidence`、`engine/events.ts`、`engine/runtime.ts`。

### 3. Agent 如何编辑，而不覆盖人的工作

**问题。** 自然语言修改可能引用不存在的素材、产生无效出口，或在模型思考期间与用户的手动编辑冲突。

**实现。** Agent 读取当前幕和素材目录，用限定的 `story_*` 工具编辑私有候选。工具层校验操作白名单、场景范围和结构；每批无效时不改变候选。最后一次编辑后必须校验；模型成功结束后，宿主再运行逻辑预览。提交时比较原 revision 与当前 revision，一致才把整轮修改保存为一个版本、一组撤销。冲突、取消、超时或失败时保留任务/候选信息，不把半成品写入作品。

**可以这样讲。** “关键是把模型提案和作品提交分开。AI 可以反复修候选，真正落盘由宿主管。revision 检查保证模型拿着旧上下文时，不会静默覆盖用户刚做的修改。”

**容易追问。**

- 范围：当前幕及已开放的作品数值/成长规则；没有给场景工具任意文件、Shell、跨幕新建或发布权限。约束来自工具实现和宿主检查，也写在指令里。
- 上下文：按分区分页读当前幕，先搜索再读 @ 引用，避免把整个作品无限塞入提示词。
- 验证：`story_preview` 使用真实数值/事件逻辑，但不解码视频、不播放声音、不检验像素布局；这些仍要浏览器试玩。
- 持久化：短事务保存任务和作品，等待模型时不持有写锁。底层是单进程本地 JSON 资料库；事务串行、临时文件写入与原子重命名。它还不是多人在线协作架构。
- AI 当前做的是场景编辑。团队制作的视频随后接入，尚未实现玩家选择后实时生成完整影片。

代码入口：`shared/scene-tools.mjs`、`server/index.mjs` 的 `runAgent`、`server/scene-preview.mjs`、`server/library-store.mjs`。

### 4. 为什么选择受限脚本运行时

**问题。** 创作者需要写条件和数值逻辑，但脚本可能死循环、返回非法数据或访问宿主页面。

**实现。** 每次用新的 QuickJS WASM runtime/context，只复制数值状态到客体，不暴露 DOM、网络或文件宿主函数。限制源码长度、8 MB 堆、128 KB 栈和 50 ms 截止时间，通过中断处理器检查截止时间。成功后解析 JSON 并验证有限数值；错误、超时或非法结果时不接收本次状态更改，最后释放上下文和运行时。

**可以这样讲。** “我们的目标先是让角色数值和分支条件可编辑，所以开放的是受限数据接口。脚本算完并校验成功，宿主才接收新数值。这样权限范围和失败语义都比较清楚。”

**容易追问。** 50 ms 是执行器设置的截止时间与中断机制，不是交互延迟承诺。同步执行仍有开销；后续若玩法更复杂，可考虑 Worker 隔离执行，并重新做性能和兼容性验证。当前不要宣称所有恶意代码都绝对安全，也不要说完整复刻了 GDevelop。

代码入口：`src/playground/engine/scripting.ts`、`engine/runtime.ts`、`engine/gdevelop.ts`。

### 5. 声音与响应式：更贴近个人工作的技术切口

**声音问题。** 切幕导致环境音重起；对白和背景一起被压低；循环边界出现空隙。

**实现。** Player 持有一个 CinematicSoundtrack，复用相同音源；原片音轨独立，出现对白时只降低环境声。音量用 GainNode 渐变，用户手势解锁 AudioContext。WAV 解析原始采样率后解码，配合素材首尾处理，避免解码重采样补零破坏循环接缝。实际耳机、扬声器和移动设备听感仍需验收。

**布局问题。** 手机直接缩小桌面 HUD 会让文字与按钮难以阅读，说明面板还可能挡住选择。

**实现。** 完整影片采用 contain；手机竖屏重新安排说明和操作。观察层用 ResizeObserver 测量信息面板高度，通过 CSS 变量给选择区留空间。平台与影片分别使用 `--theme-*` 和 `--hud-*`，避免主题修改影响影片界面。观察标记按作者标注的时间和百分比位置出现，属于屏幕空间标记。

**可以这样讲。** “适配不只是缩小。我把影片保持完整，把说明和操作按设备重排，同时按面板实际高度留出空间。这里最重要的是玩家在关键时刻能看见内容，也能完成选择。”

代码入口：`CinematicSoundtrack.ts`、`CinematicStage.tsx`、`HudFocusLayer.tsx`、`cinematic-hud.css`。

## 改写与发布的补充追问

`forkWork` 深拷贝作品，记录来源作品、来源版本和来源场景；入口 checkpoint 保存进入该幕时的数值与路线。前端同时传当前播放位置，并生成草稿封面。`publishWork` 再深拷贝成独立的 published 版本；操作协议拒绝编辑 published 作品，继续修改草稿不会改变已发布版本。角色附加到作品时同样保存快照，避免平台角色卡更新连带改写旧作品。

这套设计先保障本机原作、改写和发布版本互不覆盖；它没有提供多用户权限、版权审核或云端分发。

## 现场展示建议

1. 《第零次》进入车厢，完整播放开场，让选择出现。
2. 回应苏弥，说明选项真正跳转到接近影片；继续救治，展示钥匙与随身记录。
3. 打开工坊，说明六类 Kit、属性表单、画布与预览的关系，再回到同一幕试玩。
4. 讲 Agent 的候选—校验—版本检查—保存流程；只有在实际模型连接并完成验证时才现场演示真实修改。

本轮为核实页面内容，使用临时副本运行：实际播放开场并通过按钮进入苏弥影片，检查了 HUD 画布与舞台预览入口。没有重新调用真实模型，没有重新验收全部路线、最终声音听感或真机适配。

## 避免夸大的几句话

- 奖项可讲冠军和最佳人气奖；现场资本对接券不能写成融资到账。
- 九幕节点包含四幕缺片预览，不能说全部分支影片已完成；没有验证为完整通关的作品，不说已全量交付。
- 有场景 Agent，不代表有实时视频生成、任意世界自动生成或多 Agent 自主生产流水线。
- 本轮浏览器体验、代码核对与此前文档记录分别表述；既有验证记录不能说成今天重新全部测过。
